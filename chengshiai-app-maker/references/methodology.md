# 成事应用制造方法论

本 Skill 的方法论说明。供 Agent 理解每个阶段的意图、方法和产出，从而灵活应对不同项目，而不是机械执行问卷。

## 目录

1. 方法论总览

## 1. 方法论总览

```text
业务叙述 (Business Narrative)
→ As-Is（还原现状）
→ 问题 (Problems)
→ Root Need（真正业务需求）
→ 问题归类（类型1流程自动化 / 类型2流程重塑 / 类型3全新流程）
→ To-Be（目标工作方式）
→ Function（功能拆解）
→ Business Facts（业务事实确认：流程/数据/规则/权限/异常/输出/界面）
→ PRD（产品需求文档）
→ Architecture（技术方案，AI 自主）
→ Coding（开发，AI 自主）
→ Testing（功能验收 + 价值验收）
→ Deployment（部署）
→ Value Validation（价值验证）
```

三个关键转换：

1. **业务叙述 → Root Need**：从用户说的"想要什么"还原到"为什么要"。用户给的往往是 Solution，真正的需求藏在 Solution 背后的业务目标里。
2. **Root Need → Function**：从目标工作方式自动推导功能，而不是让用户列功能清单。用户熟悉业务，不熟悉功能建模。
3. **Business Facts → 软件**：七项设计（流程/数据/规则/权限/异常/输出/界面）把隐性业务知识显性化，成为可开发、可验收的规格。

## 2. 为什么 Business Expert 不应该被迫先成为 Product Manager

一线业务专家拥有的是**隐性知识**：他们知道每天的工作实际怎么做、哪里麻烦、数据在哪里、有哪些例外。但这些知识以经验形式存在，不是以 PRD 形式存在。

传统软件流程要求业务专家先完成一次"角色转换"——学会用产品语言表达需求（写需求文档、画原型、定义字段）。这个转换：

- **成本极高**：相当于要求专家兼职做一份陌生工作。
- **信息失真**：专家被迫用不熟悉的语言表达熟悉的事情，会丢失细节（尤其是例外情况和数据口径）。
- **责任错位**：需求写错了，锅在专家；但专家从来没有被训练过怎么写需求。

本方法论把这次角色转换交还给 AI：

- 用户用**业务语言**讲**业务事实**——这是他最擅长的。
- AI 负责分析、结构化、建模、设计、实现——这是 AI 擅长的。
- 分工边界：**技术方案 AI 决策，业务事实用户确认。**

AI 不能擅自创造业务事实（流程、数据来源、口径、规则、权限、审批关系、系统间数据关系、企业特殊规定、异常场景），因为这些只有用户知道，编造会导致软件符合想象而不符合现实。除此之外的一切分析、设计、技术决策，都不应推给用户。

## 3. 各阶段方法详解

### 3.1 业务叙述 → As-Is

用户开场只负责讲业务。三种典型入口：

- 问题驱动型（"最困扰我的是 XXX"）
- 想法驱动型（"我希望有个系统帮我 XXX"）
- 系统改造型（"我现在用 Excel/CRM 做 XXX，想优化"）

还原 As-Is 时，不要问抽象问题（"你的业务流程是什么？"），而问具体事件（"你上一次做这件事，从开始到结束怎么做的？"）。具体事件能唤起真实记忆，抽象问题只会得到概括性、失真的回答。

As-Is 的产出结构：当前目标 → 触发条件 → 步骤 → 结果，并标注每个步骤的参与人、系统、数据来源、人工/自动、易错点、耗时。

### 3.2 As-Is → 问题 → Root Need

问题识别清单（AI 主动扫描，不要求用户自己总结）：

- 重复劳动、数据重复录入、跨系统复制粘贴
- 人工搜索、人工汇总、人工判断、人工制作报告、人工提醒、人工检查
- 信息遗漏、信息不同步、数据口径不一致
- 审批等待、沟通成本
- 错误率、业务风险
- 无法追踪、无法统计、无法沉淀经验

Root Need 反推示例：

```text
表面需求：自动填 Excel
↓ 为什么填 Excel？每天整理客户跟进情况
↓ 为什么整理？让销售经理及时看到重点客户状态
↓ Root Need：重点客户状态对经理实时可见
↓ 结论：方案可能是一个状态看板，根本不需要 Excel
```

AI 自己完成大部分推理（可以内部做 Why 分析），只把关键判断交给用户确认。不要连续向用户问五遍为什么。

问题归类（与确认门1一并确认）——通过多轮对话把问题最终归为三类之一，归类决定 To-Be 的设计姿态：

1. **类型1 · 流程不变，人工变自动**：现有流程合理，只是人工操作重复耗时（如每日从各竞品网站获取竞品动态，制作竞品动态日报）。按现流程逐环节自动化。
2. **类型2 · 流程重塑**：当前流程既有人工操作，也有多个系统操作，通过一套界面供用户操作，后台按规则完成多系统对接、数据获取、规则匹配。打散重组现有系统操作。
3. **类型3 · 全新流程**：没有固定流程或线上工作流，完全重新制作一套流程/工具。从零定义流程。

### 3.3 Root Need → To-Be → Function

To-Be 设计三原则：

1. **自动化优先**：重复劳动尽量自动。
2. **人只做高价值工作**：经验、判断、审批、责任确认留给人。
3. **不自动化不该自动化的事**：法律责任、财务责任、高风险审批、不确定判断、企业敏感权限。

功能拆解从 To-Be 流程的每个环节推导，产出形如 F01～F0N 的功能清单。判断标准：每个功能都应能回答"它解决了流程中的哪个环节"。砍掉与核心问题无关的功能，第一版永远做 MVP。

范围控制用业务语言区分"必须有 / 应该有 / 以后再做"，不引入 MoSCoW 等术语。

### 3.4 Function → Business Facts（七项设计）

每个功能完成七项设计：

| 项 | 核心问题 | 谁主导 |
|----|----------|--------|
| 流程 | 谁触发、怎么走、何时结束 | 用户确认 |
| 数据 | 从哪来、怎么获取（按数据获取优先级）、谁维护、多久更新、**Source of Truth**、冲突以谁为准 | 用户确认 |
| 规则 | 执行条件、阈值、例外、部门差异 | 用户确认 |
| 权限 | 谁看/改/删/审批、数据范围 | 用户确认 |
| 异常 | 数据缺失/错误/冲突、系统失败、重复提交、中断 | AI 主动列出 + 用户确认处理方式 |
| 输出 | 记录/任务/提醒/报告/状态/文件 | AI 推导 + 用户确认 |
| 界面 | 页面结构与操作方式 | AI 设计 + 用户确认习惯 |

其中 Source of Truth 是企业应用最常见的隐性雷区：同一字段往往同时存在于 CRM、ERP、Excel、OA、飞书。不确认权威来源，系统上线第一天就会数据打架。此项**永远不得由 AI 擅自判断**。

**数据获取优先级（必须遵守）**：应用自动获取数据永远是第一选择——逐平台确认 API / 数据库权限；用户不清楚时，请用户登录网页端（用户自己操作），通过 Playwright、Computer Use 等从浏览器获取用户身份信息和 Request 接口信息，尝试直接取数，即使看起来"只能人工网页登录"也要先验证。只有确实无法自动获取时，才询问用户能否下载/导出数据并开发上传组件；仍不可行才询问是否 Mock 数据、能否提供表头。切记：未经用户确认，不得自行 Mock 数据。

异常处理采用"AI 建议式提问"：`如果发生【具体情况】，我建议【简单方案】，可以吗？`——用户只需判断，不需设计。

### 3.5 Business Facts → PRD → Architecture → Coding

- **PRD**：15 章结构（见 templates/PRD.md），是需求唯一事实来源。业务内容 ≥70%，技术内容 ≤30%。需求变更先改 PRD 再改代码。
- **技术方案**：AI 自主决策，遵循"最简单、可靠、易维护、易部署"原则。AI 必要性判断：确定性的事用代码，不确定性的认知任务用 AI。企业系统连接不假设 API 存在、也绝不假设没有 API，获取方式严格遵循数据获取优先级：自动获取（API / 数据库权限 / 从用户已登录浏览器会话获取身份信息与 Request 接口）→ 文件导入 → 用户确认后的 Mock；Mock 必须标记为模拟或临时数据源。
- **Coding**：AI 自主迭代（分析→Plan→Coding→运行→观察→修复），只有业务规则、产品方向、数据、权限、安全、成本、不可逆操作才升级给用户。必须实际运行验证，不能"写完即宣布完成"。

### 3.6 Testing → Deployment → Value Validation

测试分两层：

1. **功能验收**：软件是否按 PRD 工作（正常/边界/异常/权限/数据/规则）。
2. **价值验收**：回到项目最初的业务问题，验证是否真的解决。程序没 Bug 但业务效率没改善 ≠ 成功。

部署判断通过业务问题（自己用还是团队用、内网还是外网、有无服务器）推导技术形态，不把部署术语抛给用户。用户无技术环境时给最简单可运行方案。

价值验证的对照基准来自阶段二 As-Is 中记录的耗时/频次/错误率——这就是为什么 As-Is 阶段必须记录这些量化信息。

## 4. 贯穿全程的机制

### 4.1 三级提问

- 一级（必须问）：答案会显著改变系统设计——使用人、协作方式、敏感数据、权威数据源、权限、审批、系统连接。
- 二级（建议式确认）：AI 先给推荐方案，用户没有异议则按建议设计。
- 三级（AI 决定）：一切技术细节和交互细节，除非影响成本/安全/部署/IT 规范/维护。

判断口诀：**能推断的不问，不影响方向的不问，可以以后改的不问，只有会明显改变方案的问题才优先问。**

### 4.2 信息可信度四档

【用户已明确】/【AI推断】/【待确认】/【AI建议】。任何写入 PRD 的推断必须标注来源，不得把 AI 推断写成用户已确认的事实。

### 4.3 每步硬门

需求理解 → 功能清单 → 业务事实（逐功能逐项）→ 界面方案 → 整体 PRD → 最终验收，六道确认门。每门都要求用户明确确认后才前进；用户修改则退回该门重新确认。宁可慢，不可虚。

### 4.4 项目状态与决策记录

- `PROJECT_STATE.md`：目标、阶段、已完成、进行中、待完成、阻塞、待确认问题、已知问题。会话中断后凭此继续。
- `DECISIONS.md`：DEC-XXX 记录数据源选择、重要规则、权限、架构、范围变化，含原因、确认人、状态。防止"为什么当初这么做"被遗忘。

### 4.5 70/30 原则

两个层面：

- **沟通精力**：与用户确认的内容 70% 以上是业务（需求、逻辑、数据、规则、页面风格与设计），技术不过多打扰用户。
- **PRD 篇幅**：技术内容不超过 30%，且用业务语言简述理由。业务逻辑永远是文档的主体。

## 5. 方法论与确认关卡的关系

| 阶段 | 产出 | 确认门 |
|------|------|--------|
| 业务叙述 + As-Is + Root Need + 问题归类 | 问题理解摘要 | 门1 问题理解 |
| To-Be + 功能拆解 | 目标流程 + 功能清单 | 门2 功能清单 |
| 七项设计 | 逐功能业务事实 | 门3 业务事实 |
| 界面设计 | 页面原型/示意 | 门4 界面方案 |
| PRD 汇总 | 产品需求说明书 | 门5 整体方案 |
| 测试 + 部署 | 可用软件 + 业务价值验证 | 门6 最终验收 |

六道门全部通过 = 项目完成。任何一门未确认就前进，都视为违反方法论。
