# 成事应用开发

把业务人员的想法转化为经过确认、可以开发和验收的应用。严格执行“访谈 → 功能确认 → 异常确认 → 设计确认 → HTML PRD 确认 → 开发 → 测试 → 部署”，不得跨越确认关口。

## 开始任务

1. 建立 todo list，并在每个阶段结束时更新。
2. 阅读 [references/question-bank.md](references/question-bank.md) 和 [references/requirement-schema.md](references/requirement-schema.md)。
3. 访谈早期只在对话中维护需求台账；用户已经指定项目目录，或任务确需跨轮恢复时，再说明保存位置并写入 `requirements-state.json`。
4. 复用用户已经提供的文档、截图、网址和答案，不重复询问。
5. 每轮只问一个主要问题。不得用“以及”“同时”“还是”等连接词把两个独立信息点合并成一问；例如“谁使用”和“在哪里访问”必须分两轮。使用业务人员听得懂的口语，不要求用户理解 AI、接口、数据库或部署术语。

## 执行阶段

### 1. 开场访谈

必须把开场拆成两轮，第一轮只问：

> 你想做一个什么应用？

第二轮只问：

> 这件事现在是怎么做的，哪些地方让你觉得麻烦或不舒服？

如果用户回答不清、答案模糊或操作复杂，请用户按现在的真实做法讲述，从打开哪个系统、文件或网页开始。不要替用户编造业务事实。

继续确认使用人群、访问位置、数据共享方式和最终输出。多人使用时优先推荐共享网址访问的网页应用；只有本人使用时才优先考虑本地应用。多人仍坚持本地应用时，先说明安装、更新和数据分散的代价，并记录用户是否接受。

### 2. 询问用户本系统需要哪些功能

询问用户本系统都需要开发哪些功能。

用户回复后，先复述功能，让用户确认，并询问用户有没有补充。

如果用户一次性提出3 个及以上完整的子系统（每个包含独立的流程、数据、规则、页面），则记录下全部需求，并提示用户先聚焦实现其中一个或两个功能，开发完成后再实现另外的功能。

### 3. 逐个功能访谈和确认

逐个功能询问用户完整的执行闭环，第一个问题必须是：

> 你希望在这个功能里做哪些事情？

从回答中提炼功能操作和工作流；用户可以说功能列表，也可以直接讲工作过程。随后只追问当前功能尚不明确的正常流程、参与人员、输入输出、数据、规则、页面和外部系统。

根据业务主动推导功能需要的数据，先列出推导结果，再问是否符合真实场景；确认后询问用户目前分别怎样获得这些数据。涉及企业系统网址时，按 [references/build-test-deploy.md](references/build-test-deploy.md) 的授权和取数顺序处理。

当前功能的正常流程、数据、规则和页面明确后，根据真实流程主动发现异常。按常见程度和后果逐个询问。

待异常问题也全部清晰后，输出完整“功能需求卡”，请用户确认。未明确确认前不得进入下一个功能；用户修改后重新输出完整功能卡。

### 4. 询问设计要素

依次询问主题色、Logo、视觉风格和已有品牌素材。用户没有指定时，提出一套适合业务场景的建议并请求确认。

### 5. 先制作页面效果图

读取 [references/prd-and-mockups.md](references/prd-and-mockups.md)。根据已确认需求列出全部页面，为每个页面制作可实现的高保真效果图。优先创建浏览器可渲染的 HTML/CSS 页面原型并截图，使用真实业务字段和代表性数据，避免空泛概念图。

先把页面效果图展示给用户，征求意见并修改，直到设计方向和关键页面得到确认。需要移动端时同时提供对应效果图。

### 6. 生成并确认 HTML PRD

把最新确认的页面效果图嵌入完整 `产品需求说明书.html`。内容必须覆盖用户提供的全部信息，并按照样例 PRD 的骨架包含需求分析、应用定义、功能和操作流程、规则、数据、界面、技术要求、验收与确认记录。必须完整体现所有已确认的细节，不得用简略摘要替代已经确认的细节。

参考 [assets/prd-template.html](assets/prd-template.html) 组织内容。生成后运行：

```bash
python "<skill-directory>/scripts/validate_requirements.py" requirements-state.json --phase prd
```

把 `<skill-directory>` 替换为本 skill 的实际绝对路径，不要假设用户项目中存在 `scripts` 目录。

展示或链接 HTML，请用户审阅。根据回复同时更新需求台账、页面效果图和 HTML；循环直到用户明确回复可以开发。任何需求变更都必须先写回 `产品需求说明书.html`，再修改代码。

### 7. 开发应用

只有 `prd.confirmed` 为 true 时才能开发。读取 [references/build-test-deploy.md](references/build-test-deploy.md)，把确认的 PRD 转换成开发 todo 和验收用例，按本期功能实施，不扩展未确认范围。

默认同时交付普通用户可双击运行的启动程序：Windows 使用 `.exe`；macOS 使用 `.app`，可通过 `.dmg` 分发。双击后显示运行面板，至少包含运行状态、访问 URL、启动按钮和关闭按钮。多人通过同一网址访问时，只在负责运行应用的电脑安装程序。

### 8. 测试和对照验收

开发完成后逐项验证：

- 语法和构建正确。
- 依赖齐全。
- 应用可以启动和关闭。
- 所有已确认功能和规则可以运行。
- 接口、数据读取和失败处理正常。
- 页面与 PRD 中确认的效果图和交互一致。
- 双击启动程序及运行面板符合要求。
- 临时文件和无关测试文件已清理。

将测试证据写入需求台账，并从本 skill 的实际目录运行 `scripts/validate_requirements.py requirements-state.json --phase deployment`。测试失败时继续修复，不得把未验证的应用交给用户试用。

### 9. 部署和试用

按 PRD 中确认的本机、局域网或公网方式部署。涉及外部服务器、域名或生产环境时，在执行不可逆或外部发布操作前取得明确授权。部署后验证实际 URL，向用户提供启动方式和访问地址，请用户试用；根据试用问题修复并重新测试。

## 不可违反的规则

- 一次只问一个主要问题，不合并询问使用人群、访问地点等独立信息。
- 不把技术选型题抛给非技术用户；先问业务场景，再由 Agent 提方案。
- 不把连续处理步骤误判成多个大功能。
- 不在单个功能确认前切换到下一个功能。
- 不把“使用人数、是否同时使用”作为固定问题；仅在限额、抢占、多人同时修改、长任务或明显性能风险出现时询问。
- 不在全部正常流程明确前集中询问异常。
- 不在页面效果图确认前定稿 HTML PRD。
- 不在完整 HTML PRD 明确确认前开发。
- 不在测试全部通过前部署给用户试用。
- 不请求用户在聊天中发送账号、密码、Cookie 或验证码，不绕过企业系统权限。

## 完成检查

任务结束前检查 todo 是否全部完成，并在结果中报告：需求确认状态、页面效果图状态、HTML PRD 路径、开发与测试结果、打包文件、部署地址和未完成项。
